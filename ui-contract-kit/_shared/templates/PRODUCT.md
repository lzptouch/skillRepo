> 告诉 Agent：这个产品为谁服务、应该是什么气质、什么情况下做什么。
> 这一层解决的是「模型默认生成通用 SaaS 脸」的问题。
> 变化频率：低。由最懂产品方向的人写。

## 产品气质（Taste）

用形容词 + 具体解释，不要只写形容词：

- **{原则一，如：复杂变简单}**：渐进披露优先于一次性铺开；每屏只有一个主操作；不用 tooltip，用行内说明文字；拿不准就把元素删掉。
- **{原则二，如：面向扫描而非阅读}**：操作者每天用 200 次，界面必须可扫视、可比对、可重复操作；不要市场化的大 hero 区，不要装饰性卡片。

## 信息密度基调

明确告知 Agent 该工具属于哪一类，它会据此决定布局：

- 运营型 / SaaS 管理后台 → 克制、工具感、信息密集
- 内容型 / 消费产品 → 可以有呼吸感
- 游戏 / 创意工具 → 可以表现力强

## 硬规则（跨页面通用）

- 危险操作必须二次确认，用 Dialog，禁止 `window.confirm()`
- 错误提示必须说明「怎么恢复」，而不是只说「出错了」
- 所有列表页必须有 empty / loading / error 三态，不允许只做 happy path
- 权限不足时展示占位或「申请权限」按钮，不要直接隐藏控件（避免布局跳动）
- 新功能不靠界面文字解释自己，界面上不写「点击这里可以…」这类说明文案
