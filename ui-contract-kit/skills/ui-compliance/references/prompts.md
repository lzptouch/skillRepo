# 可直接复制的提示词

> 使用前提：项目里已有 `AGENTS.md` / `PRODUCT.md` / `DESIGN.md` / `COMPONENTS.md`。
> 没有这四个文件，提示词再漂亮也是一次性抽奖。

---

## P0 — 元提示词：让 Agent 帮你生成这套契约

```
你现在是这个项目的前端架构师。我要给你建立一套「大模型可执行的 UI 契约」，先不要写代码。

按以下顺序产出，每完成一步等我确认：

1. PRODUCT.md：我会口述产品定位和目标用户，你帮我写成品气原则 + 参考/反参考，
   原则必须带「具体到可执行」的解释，不要出现「简洁」这种空词。
2. tokens.json（W3C DTCG 格式，primitive → semantic → component 三层）+ tokens.css
3. DESIGN.md：语义 token 表（每行的用法规则必须写明）、字号阶梯、间距（4px 基准）、
   圆角上限、阴影分级、交互状态矩阵、响应式断点、Do/Don't
4. COMPONENTS.md：从我将要做的页面倒推，列出最小够用的组件集（不超过 12 个），
   每个组件写：props（含枚举值）、允许 token、必需 ARIA、必须实现的状态、
   明确标注「不接受 className」
5. AGENTS.md：常驻规则，控制在 120 行以内，把详细文档用「路由」指向上面几个文件

约束：
- 组件只在 Radix/shadcn 生态里选，不发明新抽象
- 所有互斥/易错点必须写「禁止 XXX」，而不是「建议 YYY」
- token 命名一律语义化（color.danger，不用 color.red）
```

## P1 — 生成页面规格（对标你的详细设计文档）

```
阅读 PRODUCT.md、DESIGN.md、COMPONENTS.md 和后端 OpenAPI 的 {接口名}。
为功能「{需求一句话}」产出一份 UI-SPEC，放在 specs/ui/UI-SPEC-{页面}.md。

必须包含九节：
1. 页面目标（一句话，并说明由此决定的布局取舍）
2. 信息架构（ASCII 区域块图，标 A/B/C/D）
3. 数据契约（输入字段表：类型/约束/控件/默认值；输出字段表：类型/展示方式/异常值处理）
4. 列定义（宽度/是否排序/对齐/特殊渲染）
5. 状态矩阵 —— 至少覆盖：loading、empty(无筛选)、empty(有筛选)、error、
   部分失败、超长文本、大数据量、窄屏、权限不足。
   每行写明「触发条件」和「UI 表现」
6. 交互流程（编号步骤，含 debounce、URL 同步、跳转上下文保留）
7. 无障碍要求
8. 验收标准（可勾选，逐条机器或截图可验证）
9. 明确不做（防止后续自作主张）

不要输出任何代码。写完等我校对。
```

## P2 — 布局树（先于代码的关键一步）

> ⚠️ 在 P2 之前，建议先走 **P9（灰盒）+ P10（并行候选）** 定下方向和气质，
> 再用本条把视觉决策固化成结构。跳过这两步直接写 UI-SPEC，容易在大方向上返工。

```
UI-SPEC 已确认。现在只输出这个页面的**布局树 JSON**，不要输出代码。

要求：
- 结构形如 { type: string, props: Record<string, unknown>, children?: Node[], states?: string[] }
- type 只允许取 COMPONENTS.md 里登记过的组件名
- props 里只允许出现 COMPONENTS.md 声明过的字段名，值必须是枚举值或语义 token 名
- 不允许出现任何像素值、hex、Tailwind 类名
- 每个动态节点用 states 标注它需要实现的状态

输出后对照 UI-SPEC 的「状态矩阵」自检一遍，告诉我哪些状态你在树里还没落点。
```

## P3 — 落地代码

```
布局树已确认，现在生成 React 代码。

硬约束：
- TypeScript strict，Next.js App Router
- UI 一律从 @/design-system 导入，不得手写原生 <table>/<button>/<input>
- 参照 design-system/examples/data-table.tsx 的骨架结构，只替换业务相关部分
- 只用 DESIGN.md 的语义 token
- 状态矩阵里的 {N} 个状态全部实现，不要只做 happy path
- 不允许内联 style、!important、任意 Tailwind 值、新增依赖

写完执行 npm run verify:ui，修到全绿。
```

## P4 — 视觉闭环（Playwright MCP）

```
用 Playwright 打开 http://localhost:3000/orders：
1. 分别截图 1280×800 和 375×812
2. 用 route interception 拦截 /api/v1/orders 返回 500，截图错误态
3. 返回空数组，截图空态
4. 返回 title 为 300 字符的记录，截图超长文本态
5. 注入 axe-core 跑一遍，列出所有 WCAG AA 违规

每张截图你自己看一遍，对照 UI-SPEC 列出具体偏差（间距、对齐、层级、对比度），
逐项修正后再截图，直到全部通过。最后汇报「验证了什么、在哪个视口、还剩什么问题」。
```

## P5 — Bad Output Fixer（不要重开）

```
这份实现有三处违反 DESIGN.md：
1. {具体违规} —— 应改为 {正确做法}，原因：{DESIGN.md 里的规则}
2. {具体违规} —— ...
3. {具体违规} —— ...

只修这三处，其余一行都不要动。修完说明你改了哪几行。
```

## P6 — Colleague Review（当作 PR 检查）

```
以资深前端 review 同事 PR 的标准审查这次改动，但只报硬伤：
- 有没有绕过设计系统（一次性样式、自制组件、裸值）
- 有没有漏 UI-SPEC 里的状态
- 有没有 accessibility 缺陷（焦点管理、键盘路径、对比度）
- 有没有把业务逻辑写进 design-system/
- 有没有性能问题（重复渲染、过度引入依赖）

每条给出「文件:行号 + 问题 + 改法」，不要给泛泛的建议。
```

## P7 — 从截图反推 DESIGN.md（冷启动捷径）

```
我附上几张我喜欢的产品的截图。请产出一份 DESIGN.md：
- 顶部 YAML front matter：颜色 / 字体 / 间距 / button-primary 和 input 两个组件定义
- 之后是：Overview、Colors（每个颜色写一行「什么时候用」）、Typography、Do's and Don'ts
- 要有主见：只挑 ONE 个强调色，颜色总数不超过 4 个
- 规则写成「禁止/必须」句式，不要「可以/建议」
```

## P8 — 约束重时的 CIRCLE 框架

```
Context:  我们在成熟的 monorepo 里做 {功能}，不是独立 demo
Intent:   用现有组件搭建 {页面} 的结构层次
Role:     你是严格执行组件复用的 Principal UX Engineer
Constraints: 只能用这 {N} 个组件：{list}。禁止写裸 CSS / 内联样式
Learn:    先指出这些组件覆盖不了这次需求的哪些部分（不要偷偷自己发明）
Evolve:   在以上前提下，映射出类型安全的组件树；覆盖不了的地方列成待决策清单给我
```

# 视觉先行四段式（P9 ~ P12）

> 关键原则：**用「真实渲染的 HTML 静态稿」代替生成的 mockup 图片。**
> 图是给人 Review 的投影，不是喂给模型的源文件。这套流程省掉最难也最容易出错的「图→码」翻译。

## P9 — 灰盒 wireframe（先定布局分区，不涉及视觉）

```
在 wireframe/{page}.tsx 里写一个**纯灰盒**静态页：

- 真实 DOM 结构 + 真实 Tailwind 布局类（flex / grid / gap / w-* / h-*）
- 只用灰阶：bg-gray-100 表示内容块，bg-gray-200 表示次要块，**禁止任何品牌色和圆角**
- 每个块用角标文字标注它是什么（如「A-筛选区」「D-数据表格」），字号 12px
- 用**真实长度的假数据**（订单号 32 字符、客户名 15 字），不要用 "aaa"
- 必须能在 375 / 768 / 1280 三个宽度下正常显示
- 一个文件一个页面，方便我横向对比

写完告诉我：这个页面的信息层级你是怎么分的，以及哪些区块你认为还有别的排法。
不要写任何交互逻辑，不要引入 design-system 组件。我先看结构和信息权重。
```

## P10 — 并行出 3~4 个视觉候选（挑方向，不是精修）

```
基于 wireframe/{page}.tsx 的结构，**一次性给出 4 个视觉方向的变体**，放在
wireframe/{page}-v1.tsx ~ v4.tsx，风格差异要足够明显，让我一眼能分辨：

- v1 紧凑工具型（小字号、高信息密度、无明显留白）
- v2 卡片分区型（每个区块一张卡、留白充足）
- v3 左重右轻型（导航/筛选在左，内容在右）
- v4 你推荐的第四种（说明为什么）

统一约束：
- 都用 DESIGN.md 里的语义 token，禁止裸值
- 都用 COMPONENTS.md 里的组件（可以有取舍，但要说明缺什么）
- 都带上至少三个真实数据量的行/条目

生成后你自己跑 Playwright 截图 1280×800，**把 4 张截图拼成一张 contact sheet**，
每张下面标 v1~v4 和一句话自评（这个方案最擅长什么、代价是什么）。

我会挑一个方向，或者指定「v2 的布局 + v1 的密度」。在你接到我的选择之前，不要开始精修。
```

## P11 — 反提取：把选中的视觉稿固化成契约（**命门，不要跳过**）

```
v{N} 是选定的方向。现在把这份视觉决策固化成机器可读的东西，而不是直接写正式代码：

1. 输出/更新 design-system/tokens.json：把它用到的颜色、间距、圆角、字号
   全部收敛成**语义命名**的 token（命名规则见 DESIGN.md）
2. 输出这个页面的**布局树 JSON**（type + props + children + states）
3. 列出 v{N} 里有、但 COMPONENTS.md 目前没有的能力，按「现有组件能满足/需要新组件」分类
4. 更新 DESIGN.md 的 Do/Don't：把这次评审里我认可的和不认可的写法各写 1~3 条
5. 对照 UI-SPEC 的状态矩阵，标注布局树里还没有落点的状态

第 3 步里「需要新组件」的部分先问我，不要自己创建。
这份输出确认后，才算拿到写代码的路条。
```

## P12 — 跨页面一致性 contact sheet（图片唯一不可替代的场景）

```
把这个模块的所有页面 {列出路由} 用 Playwright 在同一视口（1280×800）截图，
拼成一张 contact sheet，然后做横向一致性检查：

逐项比对，列出所有「不同页面做得不一样」的地方：
- 同类操作的按钮层级（同一动作在不同页是否都是 primary）
- 同类区块的间距与卡片样式
- 表格/列表的行高、字号、对齐
- 空状态与错误状态的措辞和位置
- 页面标题的字号与位置

每条给出「页面A vs 页面B + 具体差异 + 建议以哪个为准」。
只报真实差异，不要报你觉得"应该优化"的东西。
```

## 什么时候才真的需要「生成图片」

只有两种情况值得出 mockup 图，**并且出完一定要走 P11 把决策固化**：

1. **完全没方向、连布局分区都定不下来** —— 出图帮你找感觉，然后立刻丢弃。
2. **给非技术干系人汇报** —— 老板看不懂 wireframe 和 JSON。

除此之外，一律用 HTML 静态稿。它既是"图"，又已经是代码，没有翻译损失。
