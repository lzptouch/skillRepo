# pbs-build-module · 生成可复用模块

## 五关准入（缺一不可，缺任何一关都不得入册）

| 关 | 要求 | 为什么 |
|---|---|---|
| 1. 接口边界清晰 | 输入/输出/异常/副作用全部写明 | 边界模糊的片段 AI 不敢用，等于没存 |
| 2. 有测试且能一条命令跑通 | `test_cmd` 必须可直接执行 | 复用省的是验证，没测试 = 还得审一遍 = 白干 |
| 3. 有好/坏示例 | README 里各一个可复制的最小示例 | AI 看例子比看描述有效得多 |
| 4. 有使用记录 | `used_by` 列表 | 三次法则的计数器，也是季度清理依据 |
| 5. 登记进 `registry.json` | AI 可检索 | 检索不到 = 不存在 |

## 何时使用

- `pbs-spec-flow` 完成后
- 用户明确要求把某个能力做成独立模块

## 输入

| 参数 | 必填 | 说明 |
|---|---|---|
| flow 目录 | 是 | `<资产库>/flows/<name>/` |
| 目标语言 | 否 | 从 flow 的 implementation-notes 推断 |
| 资产库路径 | 否 | 默认 `~/pbs` |
| 首批使用项目 | 是 | 至少 1 个，写进 `used_by` |

## 流程

### 第 1 步 · 建目录（严格按此结构）

```
<资产库>/modules/<lang>/<name>/
├── src/                 # 实现，纯逻辑，禁止依赖具体业务
├── tests/               # 单元测试 + 集成测试
├── fixtures/            # 测试数据（pbs-validate-module 会用到）
├── module.yaml          # 元数据（模板 assets/module.yaml.tmpl）
├── README.md            # 接口 + 好/坏示例 + 边界（模板 assets/README.module.tmpl.md）
└── CHANGELOG.md
```

若是 UI 组件，额外产出 `stories/` 或 `.stories.tsx`（视觉/交互回归用）。

### 第 2 步 · 写实现（三条纪律）

1. **依赖倒置**：外部服务通过参数注入，不要在模块内部 `new Redis()` / 读全局环境变量。这是「换个项目还能用」的前提。
2. **显式失败**：禁止 `catch {}` 吞异常。GitClear 2026 数据显示 AI 生成的错误掩盖结构增加了 47% —— 这类代码在本地能跑，在生产是哑火事故。每个 catch 必须：记录原因、或转成明确错误类型向上抛。
3. **不要为假想需求留扩展点**：YAGNI。只有真实出现过的使用场景才写进接口。

### 第 3 步 · 写测试（三层，不许跳）

| 层 | 覆盖什么 | 数量参考 |
|---|---|---|
| 单元 | 正常路径 + 每个边界条件 | 每个公开函数 ≥3 例 |
| 异常 | 非法输入、超时、外部依赖失败 | 每个失败模式 1 例 |
| 契约 | 输出结构/类型不变（防以后改坏） | 1 例 |

fixtures 至少包含：`happy.json` / `edge.json`（边界：空、极大、极值、特殊字符）/ `error.json`。

### 第 4 步 · 写 README（用模板）

最关键的三段：**最小可用示例**、**坏例子对照**、**什么时候不要用**。第三段最常被省略，也最能防止误用。

### 第 5 步 · 登记进 registry.json

格式见 `assets/registry-entry.json`。要点：

- `keywords` 要写**中英文 + 同义词 + 常见叫法**（用户会用不同词搜）
- `summary` 一句话说清「什么时候该用它」
- `exports` 列出全部公开 API
- `test` 填可直接执行的命令
- `used_by` 填真实项目

登记后**立刻验证可被检索到**：

```bash
rg -i "<其中一个关键词>" <资产库>/registry.json
```

### 第 6 步 · 回头更新 flow

把生成过程中发现的新约束回写进 `flow.md` 的 `Constraints` 段。flow 和 module 是同一份真相的两面，不允许漂移。

## 硬性规则

- **没有通过测试的模块不许登记**。这是本 skill 的红线 —— 一个没测试的模块进库，等于往资产库里扔定时炸弹，AI 会检索到它并自信地用上。
- **不要一次生成多个模块**。一次一个，测试与检查都通过后再做下一个。
- **不要复制原项目的代码**。按 flow 重写 —— 原代码耦合了业务上下文，直接搬会把耦合一起带进来。
- 完成后必须提示用户下一步：跑 `pbs-audit-module`（静态检查）和 `pbs-validate-module`（数据检测与跑通）。
