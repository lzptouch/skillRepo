# pbs-spec-flow · 把隐性做法变成显式流程

## 原理

代码可以被 AI 秒级重写，真正值钱的是**做这件事的正确顺序和边界判断**。本 skill 把散落在项目里的隐性知识抽出来，变成两类产物：给人和 AI 读的**契约**，以及 AI 能直接执行的**流程 skill**。

同时这也是一道安全闸：先有流程契约，再生成模块，避免 AI 在没有边界的情况下自由发挥。

## 何时使用

- `pbs-analyze` 输出了候选，用户确认了要提取其中某一项
- 用户想把某个「每次都要跟 AI 解释一遍怎么做」的事情固化下来
- 在 `pbs-build-module` **之前**调用（顺序不能反）

## 输入

| 参数 | 必填 | 说明 |
|---|---|---|
| 源文件/目录 | 是 | 候选所在位置（来自分析报告） |
| 能力名称 | 是 | kebab-case，如 `third-party-file-upload` |
| 输出目录 | 否 | 默认 `<资产库>/flows/<name>/` |

## 流程

### 第 1 步 · 追一遍真实执行路径

不要读单个文件，要**从入口追到出口**，把整条链路走一遍：

```bash
rg -n "<入口关键词>" <project>/src -A 30
```

必须回答清楚：

- 谁调用它、在什么时机调用（前置条件）
- 中间做了哪几件事（按顺序，标出每件事落在哪个文件哪几行）
- 和外部系统在哪里交互（DB / HTTP / 文件 / 队列 / 第三方 SDK）
- 失败在哪里发生、当前是怎么处理的（**重点看有没有吞异常**）
- 最终返回什么 / 产生什么副作用

### 第 2 步 · 写流程契约 `flow.md`

模板见 `assets/flow.tmpl.md`。六要素缺一不可，缺一个 AI 就会自由发挥：

| 要素 | 要求 |
|---|---|
| Problem | 这个能力解决什么问题，不解决什么 |
| Preconditions | 前置条件（环境、配置、依赖服务） |
| Steps | 有序步骤，每步标输入输出 |
| Boundaries | **必须写明 Non-Goals**：什么不做 |
| Failure modes | 每种失败怎么表现、怎么恢复、禁止吞异常 |
| Acceptance | **可测试的验收标准**（不是「ui 好看」，而是「1MB 文件上传 P95 < 2s」） |

**粒度自检（很重要）**：问自己——*「换个技术栈实现，这份 flow 还成立吗？」* 成立说明写的是 WHAT；不成立说明你把 HOW 混进来了，把技术细节挪到 `implementation-notes.md` 里去。

### 第 3 步 · 抽出接口签名

从代码里提炼，不要发明：

```
输入：<类型> <名字> —— 约束（必填？范围？格式？）
输出：<类型> —— 成功时什么样
异常：<错误类型> —— 什么情况抛
副作用：是否会写库 / 发消息 / 产生费用
```

### 第 4 步 · 生成可执行 SKILL.md

把 flow 编译成 AI 能直接跑的 skill（模板见 `assets/skill.tmpl.md`）。要求：

- frontmatter 只写 `name` / `description` / `license` / `metadata`（**跨工具兼容的唯一写法**，不要写任何厂商私有字段）
- `description` 里**把触发关键词放在最前面**（部分工具会截断 description 做匹配）
- 正文 **≤150 行**（超了就拆分 —— 臃肿的指令文件不会提升成功率，还会让推理成本 +20%）
- 命令放最前面，带完整 flag
- 每个约定配一个「好例子 / 坏例子」，不要描述风格，直接展示
- 写「禁止清单」，比写「应该」有效得多
- 资源引用一律用相对 skill 根目录的一层路径：`scripts/`、`assets/`、`references/`

### 第 5 步 · 标注 hallucinations 风险点

列出这份流程里 AI 最容易做错的地方（幻觉 API、过时的库用法、本项目特有的坑）。这份清单会直接变成 `pbs-audit-module` 的检查项。

## 输出产物

```
<资产库>/flows/<name>/
├── flow.md                  # 契约：做什么、边界、验收
├── interface.md             # 接口签名 + 约束
├── implementation-notes.md  # 技术栈相关的 HOW（可换）
└── SKILL.md                 # 可执行流程（可复制到 skills/ 下直接启用）
```

## 硬性规则

- **不要美化原始实现**。如果原实现里有 bug 或坏味道，在 `flow.md` 里明确指出「原实现此处有问题，新版本应当……」，否则你会把 bug 一起沉淀进资产库
- **Non-Goals 必须写**。这是防止 AI 过度设计最有效的一栏
- 用例面积 Path：这份 flow 要能直接支撑下一步生成模块，凡是模块生成时需要的信息都必须已经落在文档里
- 完成后告诉用户：`flow.md` 已就绪，下一步跑 `pbs-build-module`
