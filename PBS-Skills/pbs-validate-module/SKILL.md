# pbs-validate-module · 数据检测与跑通验证

## 原理

静态检查（`pbs-audit-module`）证明代码「看起来对」，数据检测证明它「真的能用」。AI 生成的组件常常只在它被生成的那一个上下文里跑过一次 —— 边界、异常、并发、脏数据全都没验证过。**本 skill 就是把「只跑过一次」变成「在各种情况下都跑过」。**

## 何时使用

- `pbs-build-module` 之后、`pbs-audit-module` 之后，**入库前的最后一道关**
- 引用一个老模块到新项目之前
- 季度资产库复审

## 输入

| 参数 | 默认 | 说明 |
|---|---|---|
| 模块路径 | 必填 | `<资产库>/modules/<lang>/<name>/` |
| 是否需要真实外部依赖 | `mock` | `mock` / `container`（起 docker 依赖）/ `real`（连真实服务） |
| 覆盖率门槛 | 80% | A 类（安全/核心）模块要求 ≥90% |

## 流程

### 第 1 步 · 准备测试数据（五类，缺一类就不算跑通）

按 `assets/fixtures-checklist.md` 构造：

| 类别 | 例子 |
|---|---|
| **正常** | 典型输入、常见规模 |
| **边界** | 空值、空数组、0、极大值、最大值±1、超长字符串、特殊字符/emoji/多字节 |
| **非法** | 类型错误、缺必填、格式错误、越权输入 |
| **脏数据** | 上游真实产生过的脏输入（重复、部分缺失、编码问题） |
| **规模** | 批量 1k/10k 条 —— 暴露 O(n²) 和内存问题 |

数据放在 `<module>/fixtures/`，命名 `<case>.<ext>`。**不要用 happy path 的单一 fixture 充数。**

### 第 2 步 · 跑测试

```bash
# 按语言选择，示例：
pnpm vitest run <module>/tests --coverage
pytest <module>/tests -v --cov=<module>/src
go test ./<module>/... -cover
```

要求：

- **全部通过**，允许 0 个 skip、0 个 todo（有 skip 必须写明原因并得到用户同意）
- 覆盖率达到门槛
- **契约测试必须通过**（保证以后改模块不会静默破坏调用方）

失败处理：区分是**模块 bug** 还是**测试用例写错**。若 fixture 不合理，改 fixture；若模块逻辑错，回 `pbs-build-module`。

### 第 3 步 · 外部依赖处理

- `mock` 模式：所有外部调用必须可注入并被 mock，断言「调用了几次、传了什么参数」
- `container` 模式：起真实依赖（docker compose），测真实协议行为
- **`real` 模式必须先经用户同意**，且禁止对生产数据做写操作

### 第 4 步 · 失败注入

主动注入以下常见故障，逐个验证：

- 外部依赖超时 / 返回 500 / 返回畸形 JSON
- 数据库连接断开
- 并发调用（同一实例多次 / 竞态）
- 重复调用幂等性（同一入参调两次，结果一致）

每项都得有断言，且断言必须检查**错误信息是否可读**（不能只是 `null`）。

### 第 5 步 · 集成冒烟（最小可用）

写一个 `smoke.test.*`：像真实调用方那样，从模块入口走一遍最典型路径。**这一条最容易被跳过，也最容易暴露问题** —— 因为它测的是「别人能不能把它用起来」，而不是「函数对不对」。

### 第 6 步 · 输出验证报告

写到 `<module>/VALIDATION.md`：

```
# 验证报告 · <name>
## 测试执行
命令 / 通过数 / 失败数 / 耗时 / 覆盖率

## 数据覆盖矩阵
| 用例类别 | 用例数 | 通过 | 覆盖到的分支 |
|---|---|---|---|

## 失败注入结果
| 故障类型 | 期望行为 | 实际行为 | 结论 |
|---|---|---|---|

## 已知限制（必须写）
- 未覆盖的场景
- 依赖的外部条件
- 性能基线（如有）

## 结论
可入库 / 不可入库（阻塞项清单）
```

## 硬性规则

- **测试不通过就不许登记/更新 registry**。这是全套 skill 的最后闸门。
- **「已知限制」必须写**。诚实标注未覆盖场景，比假装全绿有价值得多 —— 因为下一次引用的人就是你自己。
- **不要为了让测试通过而弱化断言**（比如把 `expect(x).toBe(1)` 改成 `expect(x).toBeTruthy()`）。这是最常见的自欺。
- 完成后把结果摘要念给用户：**通过数、覆盖率、失败注入结论、是否可入库**。
