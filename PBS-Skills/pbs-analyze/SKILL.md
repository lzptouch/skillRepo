# pbs-analyze · 项目可复用性分析

## 原理（决定了本 skill 的一切取舍）

AI 时代复用真正省的是**验证**不是打字。一个 300 行模块让 AI 重写，生成只要 5 分钟，但人要审 30–60 分钟；引用已验证模块则几乎不用审。

所以「值得提取」的唯一标准是：**沉淀一次之后，未来每次引用能省掉多少审查量**。通用但每次都要重审的东西（比如一段没测试的工具函数）不值得入册。

## 何时使用

- 一个项目刚做完或阶段性完成，想把它变成资产
- 想清理某个老项目，看有什么能留下
- `pbs-harvest` 的第 1 步会自动调用本 skill

## 输入

向用户确认（缺失时给默认值）：

| 参数 | 默认 | 说明 |
|---|---|---|
| 项目路径 | 必填 | 绝对路径 |
| 资产库路径 | `~/pbs` | 已存在的 PBS 资产栈，没有就用本次输出代替 |
| 深度 | `standard` | `quick`=只看结构与依赖；`standard`=含重复检测；`deep`=含逐文件耦合分析 |

## 流程

### 第 1 步 · 摸清项目骨架（不要跳过）

```bash
# 规模与语言分布（没有 cloc 就用 find/stat 粗算）
cloc <project> --exclude-dir=node_modules,dist,.git,vendor
# 技术栈与依赖
cat <project>/package.json <project>/requirements.txt <project>/go.mod 2>/dev/null
# 顶层结构
find <project> -maxdepth 2 -type d -not -path "*/node_modules*" -not -path "*/.git*"
```

产出一张「项目地图」：入口在哪、数据怎么流、外部依赖有哪些、配置怎么注入。**这张图是后面所有判断的基础。**

### 第 2 步 · 找重复（项目的自我暴露）

重复是模式浮现的最强信号。

```bash
# 通用重复检测（支持多语言）
npx --yes jscpd <project>/src --min-lines 5 --reporters json
# 轻量替代：找同名/近似名文件
rg --files <project> | rg -i "util|helper|common|shared|client|wrapper|adapter"
```

把「项目内出现 ≥2 次的实现」单独列出来 —— 这已经是真实的第二次使用，下一步就该抽象。

### 第 3 步 · 按三类候选归类

| 类别 | 判定条件 | 处置 |
|---|---|---|
| **A · 例外类** | 属于「基础设施 / 领域核心 / 安全」三类之一：DB 连接、日志、配置、HTTP 客户端、错误码；金额计算、权限校验、状态机；加密、认证、输入 sanitize | **第一次就该提取**，不用等三次法则 |
| **B · 重复类** | 项目内重复 ≥2 次，或跨项目已知重复 | **优先提取**，模式已浮现 |
| **C · 通用单次类** | 只出现一次但明显通用（第三方 API 封装、某种文件解析、某类页面模板） | **登记观察**，放进 `_incubator/`，不正式提取 |

**不要碰的**：与业务逻辑深度耦合的胶水代码、一次性的数据迁移脚本、只在本项目语境下有意义的类型定义。

### 第 4 步 · 逐项打分（五项，每项 0–5）

| 维度 | 打分依据 |
|---|---|
| **通用性** | 脱离本项目还能用吗？换个同类项目是否直接可用 |
| **频次预期** | 未来 6 个月会用到几次？≥3 满分 |
| **验证负担** | 重写一次要审多少行？负担越大越值得提 |
| **接口清晰度** | 能否一句话说清输入/输出/边界？含糊的直接扣分 |
| **提取成本** | 与业务的耦合度。改 3 行就能剥离=5 分；要拆解重写=1 分 |

总分 ≥18 提取，12–17 进孵化区，<12 放弃。**宁缺毋滥：一次分析推荐不超过 5 个正式候选。**

### 第 5 步 · 输出报告

写到 `<output>/PBS-ANALYSIS.md`（默认 `<项目>/.pbs/PBS-ANALYSIS.md`），结构：

```
# 可复用资产分析 · <项目名>
## 1. 项目地图        （骨架、依赖、数据流）
## 2. 重复热点        （文件、行数、重复次数）
## 3. 候选清单        （表格：类别 / 名称 / 位置 / 五项得分 / 总分 / 处置）
## 4. 逐候选详解      （接口现状、当前有无测试、耦合点、建议的模块边界）
## 5. 不建议提取的清单 + 理由
## 6. 下一步          （建议对哪几个跑 pbs-spec-flow）
```

## 硬性规则

- **先读代码再下结论**，不要凭目录名猜（`utils/` 里往往一半是垃圾）
- **不要推荐没有明确接口边界的东西** —— Extractor 得分直接记 0
- **不要为了凑数把业务逻辑硬说成通用模块**
- 报告里每一项都要给出**文件级证据**（路径 + 行号），方便用户复核
- 分析完**必须**把候选清单念给用户，等确认后再进入 `pbs-spec-flow`
